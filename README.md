# fanM — 無限のfantasyMSX

fanMは、AIがMSX風のデモを継続的に制作し、Webサイトに自動で公開するプロジェクトです。

常時稼働するホストの上でバッチ処理がAIのAPIを呼び出し、企画、TypeScriptの生成、動作確認、修正、公開までを自動で進めます。人間は、たまにギャラリーサイトを開いて、溜まった作品を楽しみます。

目指すのは、**月3,000円程度の負担で、一週間放置しても作品が増えていること**です。日々のお題出し、コードの修正、作品の選別、公開の承認を利用者に求めません。

このREADMEは、これから実装するプロジェクトの方針を記したものです。記載している機能や設定は、現時点で実装済みであることを意味しません。

## 二つの部分

fanMは、作品を作る側と見せる側の二つに分かれます。

| | 役割 | 動く場所 | ディレクトリ |
| --- | --- | --- | --- |
| **バッチ処理** | 企画、生成、検証、修正、予算管理、作品の保存、公開 | ホスト「chevron」上で、Coolifyが管理するコンテナとして常駐 | `packages/batch` |
| **ギャラリーサイト** | 作品の目録、サムネイル、ブラウザでの再生 | Cloudflare Workers（静的アセットの配信） | `packages/gallery` |

二つは直接は通信しません。バッチ処理が作品をギャラリー用の静的ファイルとして書き出し、Cloudflareへ送ります。ギャラリーは閲覧時にAIのAPIを呼ばず、バッチ処理が止まっていても表示できます。

両者が共有するのは、作品の形式（`packages/work`）とfantasy-msxのエンジン（`engine/fantasy-msx`）だけです。

## fantasy-msxとの関係

[fantasy-msx](https://github.com/sylx/fantasy-msx)は、MSXの映像・音源チップを使ったアプリケーションをTypeScriptで書くための実行基盤です。fanMは、それを内包する別プロジェクトとして、制作と公開を自動化します。

- **fantasy-msx**：画面、音、入力、アプリケーションの実行を担当する。
- **fanM**：企画、生成、検証、予算管理、作品の保存、公開、鑑賞を担当する。

fantasy-msxはgit submoduleとして特定のコミットに固定して利用します。エンジンの更新は作品生成とは別に扱い、生成されたコードがエンジンやバッチ処理を書き換える構成にはしません。

## 利用体験

初回にAIのAPIキー、公開先、予算を設定したら、普段の制作への関与は不要です。

1. バッチ処理が、設定した頻度で制作を始める。
2. AIが企画を考え、デモを生成する。
3. ヘッドレス環境で実行し、必要なら自動で修正する。
4. 検査を通った作品が、タイトル、説明、サムネイルとともにギャラリーへ公開される。
5. 利用者は好きなときにギャラリーを訪れ、新着や過去作品を見る。

ホストの停止やコンテナの再デプロイで制作が止まっても、公開済みのギャラリーは引き続き閲覧できます。制作は再開後に続きから進めます。停止中の予定をすべて取り戻そうとして、再開直後に大量生成することは避けます。

## 全体構成

```text
chevron（Coolify）
  バッチ処理コンテナ
    スケジューラー・予算管理
      → 企画
      → AI APIによるコード生成
      → ビルド・実行・撮影
      → 自動検査・必要に応じた修正
      → 作品保存・公開待ちキュー
      → 定期的にCloudflareへ送る
  永続ボリューム
    ジョブ状態・予算台帳・作品庫・ログ

Cloudflare Workers
  ギャラリーサイト
    作品の目録・サムネイル
      → 新着・過去作品・ランダム再生
      → ブラウザ上でfantasy-msxを実行
```

ギャラリーには静的ファイルだけを置きます。生成頻度と公開頻度は分け、複数作品をまとめて公開できるようにします。作品はWorkersの静的アセットとして送ります（`wrangler deploy`）。一度出したファイルは中身も名前も変わらないので、作品が増えても送られるのは増えた分だけです。公開先は `fanm.oyabanare.com`、手順は [docs/deploy.md](docs/deploy.md) にあります。

特定のAI事業者や公開先への依存は、接続部分に閉じ込めます。

## 自動制作の流れ

### 企画

過去作品の短い要約と制作ルールをもとに、AIが次の企画を決めます。利用者が毎回プロンプトを書く必要はありません。

題材、動き、構図、操作、音、利用するMSXの機能などを変え、既存作品の色や名前だけを変えたものに偏らないようにします。過去の全コードや会話履歴を毎回渡すのではなく、必要な情報を要約して保持します。

### 生成

AIには、作品の共通形式、fantasy-msxのAPI資料、小さな実例、制作上の制約を渡します。生成対象は作品のコードと素材、メタデータです。

最初は、無操作でも30〜60秒程度楽しめる短い作品を中心にします。操作できる作品も、開始操作を待ち続けず、自動で見どころまで進むことを基本とします。

映像は描画コードやスプライト、音楽はMMLや音源制御で制作します。追加の画像・音楽生成サービスや、作品実行時の外部APIを必須にしません。

### 実行と検査

fantasy-msxのヘッドレス実行、フレーム送り、入力注入、画像・音声出力を土台に、生成された作品を実際に動かします。ブラウザでの実行確認も行い、ヘッドレス環境だけでは見つからない読込や描画の問題を確認します。

検査するのは、型やビルドのエラー、実行時例外、タイムアウト、素材の読込失敗、描画待ちの増大などです。複数時点の画面も取得し、必要に応じてAIへ返します。

静かな作品やゆっくり変化する作品を一律に失敗と扱わず、企画に照らして判断します。面白さの評価は補助に留め、明らかな不具合や重複を減らすことを優先します。

### 修正と採用

失敗した場合は、エラーや撮影結果をAIへ渡して修正します。修正回数と一作品に使う予算には上限を設けます。初期値は最大2回の修正を想定します。

上限までに成立しなければ、その作品は不採用として記録し、次の制作へ進みます。失敗した作品の修正を利用者に依頼しません。

検査を通った作品は自動で採用します。公開のための人間の承認工程は設けません。

## 無人運転のためのルール

| 状況 | 自動処理 |
| --- | --- |
| 作品の生成や実行に失敗 | 上限内で修正し、直らなければ不採用にする |
| APIが一時的に利用できない | 待ち時間を延ばしながら、上限付きで再試行する |
| 公開に失敗 | 成果物を保持し、生成し直さず公開だけ再試行する |
| コンテナやホストが停止・再デプロイ | 永続ボリュームに保存されたジョブ状態から再開する |
| 月間予算に達する | 新しいAPI呼出しを止め、翌月に再開する |
| 認証切れなど自動復旧できない問題 | 該当処理を停止し、利用者に知らせる |

ジョブには識別子を付け、再試行で同じ作品が重複公開されないようにします。公開が失敗した場合も、直前の正常なギャラリーを維持します。

日常的な作品の失敗はログに残し、通知で利用者を呼び戻しません。人間の対応が必要な運用上の問題だけを通知対象にします。

状態はすべて永続ボリュームに置き、コンテナのイメージには含めません。イメージを作り直しても、使用額、ジョブ、作品庫は失われません。

## 予算

継続運用の目安は**月3,000円程度**です。AI APIを主な費用とし、ギャラリーはCloudflareの無料枠に収めることを目指します。有料ドメインは必須にしません。chevronの運用費は別途です。

ドル建てAPIを使う場合は、為替や税の余裕を取り、まず月12〜15ドル程度のAPI上限から調整することを想定します。これは固定の換算レートや請求額を保証するものではありません。

- 企画、検査、思考トークン、修正、不採用作品を含め、すべてのAPI利用を予算に計上する。
- 月間上限、一作品の上限、各呼出しの出力上限を設ける。
- 呼出し前に最大想定費用を予約し、完了後に実際の利用量で精算する。
- 請求の有無が不明な失敗は、費用を安易にゼロとして扱わない。
- 予算台帳を永続化し、再起動や再デプロイのあとも使用額を忘れない。
- 月の前半で使い切らないよう、残予算と残日数から制作頻度を調整する。

モデルの単価だけでなく、**公開できた一作品あたりの費用**を測ります。安いモデルでも修正や不採用が多ければ効率は下がるため、モデルと生成頻度は実測に基づいて選びます。

最初は一日3〜5試行程度から始めます。公開作品数は固定せず、予算と成功率に応じて変わるものとします。

## 作品の保存と再生

作品ごとに、次の情報を保存します。

- タイトル、説明、操作方法、制作日時
- 実行可能な成果物、ソースコード、使用素材、サムネイル
- fantasy-msxのバージョンと乱数seed
- 検証時の入力シナリオと撮影タイミング
- 制作に使ったモデル、指示、検査結果、利用量、費用

ギャラリーに出す情報とバッチ側の制作記録は分け、認証情報や内部ログを公開成果物に含めません。採用済み作品は次回の生成でも保持し、不採用作品の詳細ログや検査用録画には保存期間・容量の上限を設けます。

作品は起動ごとに状態を初期化できる形式にします。時刻はフレーム基準、乱数はseed付きとし、素材の準備完了を待ってから再生を開始できるようにします。

ギャラリーは固定のプレイヤーと目録で構成し、作品を個別に読み込みます。初期機能は新着順の一覧、作品ごとのURL、ランダム再生とします。連続再生やお気に入りは、その後に追加できます。

## 実行環境の分離

生成コードは、時間・メモリ・アクセス先を制限した隔離環境で検査し、停止しないコードも外から終了できるようにします。

AIのAPIキーとCloudflareの認証情報はバッチ処理が管理し、生成コードには渡しません。認証情報はCoolifyの環境変数で渡し、イメージやリポジトリには含めません。生成コードが任意の依存パッケージを導入したり、ホストのファイルを読み書きしたりする必要のない構成にします。

ギャラリーでも、作品を隔離したフレーム内で実行し、切替時に実行環境を破棄します。一作品の不具合が目録や他の作品に影響しないようにします。

## 最初に実装する範囲

1. fantasy-msxを固定した版で内包し、作品形式と最小テンプレートを決める。
2. 一つのAI APIに接続し、企画から生成まで実行する。
3. ビルド、実行、撮影、自動修正を一つのジョブとして回す。
4. ジョブ状態と予算を保存し、定期実行と再開を可能にする。バッチ処理をコンテナにし、chevronのCoolifyで常駐させる。
5. 採用作を作品庫へ追加し、Cloudflare Workers上のギャラリーへ自動公開する。
6. 一週間、人の介入なしで運転して費用と結果を確認する。

初期段階では、分散実行、多数のモデルによる合議、画像生成サービスとの連携、利用者ごとの作品生成などは導入しません。一つのバッチ処理、一つの制作キュー、一つのギャラリーから始めます。

## 最初の到達点

**一週間放置したあとにギャラリーを開くと、新しい作品が溜まっている。途中の失敗は自動処理され、費用は設定予算内に収まっている。**

生成試行数、公開作品数、不採用理由、公開一件あたりの費用、人の対応が必要だった回数を記録し、この状態を安定して続けられるかを確認します。

## 開発

ディレクトリ構成、fantasy-msxの組み込み方、作品形式は [docs/architecture.md](docs/architecture.md) にまとめています。

```bash
git submodule update --init
npm install
npm run typecheck
npm run check:templates       # バッチ：5つのテンプレートをヘッドレスで動かして撮影
npm run gallery:dev           # ギャラリー：play.html?work=ambient でテンプレートを再生
npm run publish:local         # 公開物を var/site/ に組み立てる（どこへも送らない）
npm run start:fake -- --once  # 偽のAIで制作の輪を一周（企画から公開物の組み立てまで）
npm start                     # 常駐して作り続ける。本番（Coolify）が動かすのもこれ
npm run status                # いまどうなっているか
```

Cloudflareへの公開（`npm run publish`）には `CLOUDFLARE_API_TOKEN` と `CLOUDFLARE_ACCOUNT_ID` が要ります。[docs/deploy.md](docs/deploy.md) を参照してください。

常駐の仕組み（頻度の決め方、人を呼ぶ条件、コンテナ、Coolifyへの置き方）は [docs/operate.md](docs/operate.md) にまとめています。
